# 设备验证说明

本说明区分代码层检查、隔离原生检查和真实设备验证，避免将某一层的成功当成完整的同步保证。

## 当前发布状态

版本 **0.3.1** 以 **Obsidian API 版本 1.13.7 桌面构建的已知内部方法指纹**为兼容基线。移动端（手机与 iPad）可以编辑本机矩阵草稿，原生排除项默认只读；只有运行 API 版本为 1.13.7、12 个方法指纹全部匹配、本机隔离过滤检查通过，并且用户在本机明确开启“允许在这台手机或平板上修改同步设置（实验功能）”，才允许预览后手动应用，或在开启自动处理时对首次登记的新插件应用。实验确认只存本地，不能绕过版本或指纹门禁。

手机与 iPad 显示 1.13.7 仅提供版本信息，不是方法匹配或传输正确性的证明。两台设备的本机指纹是否匹配仍待检查，真实移动端同步仍未验证。开启实验选项也不改变这一状态。0.3.0 新增安装来源识别与自动处理，本轮没有通过实际安装新插件验证该流程；以下自动流程用例仍属于待执行验收。

| 验证层 | 能回答的问题 | 不能据此推出的结论 |
| --- | --- | --- |
| 类型检查与项目测试 | 规则、排除路径、所有权与操作日志逻辑是否符合测试用例 | 真实 Obsidian 或网络同步一定正确 |
| 桌面源构建与指纹核对 | 被检查的方法是否与已记录的桌面实现一致 | 相同版本的手机/iPad 实现也一致 |
| 隔离原生过滤检查 | 指定插件目录被排除、相邻路径及无关笔记不被误排除 | 实际上传/下载已停止，或进行中的传输已经取消 |
| 新安装识别与自动处理的模拟测试 | 来源默认值、新 ID 合并、升级基线、等待与重试逻辑是否符合用例 | 真正的官方安装入口、手机安装或多设备网络顺序已经验证 |
| 原生保存调用完成 | 原生保存 Promise 返回，当前内存列表符合预览 | 重启之后一定保留，或远端已完成同步 |
| 真实设备端到端验证 | 指定设备上有证据支持上传、下载、恢复与重启行为 | 所有版本、平台、竞态和异常都已覆盖 |

实际测试结果应附上命令输出、日期、平台、Obsidian 版本和对应构建；不要把本说明中的待验证步骤标成已经通过。发布前仍需记录真实 Sync 网络、手机/iPad 端到端、重启持久化和进行中传输行为的结果。

## 可复现的离线检查

在源码目录执行：

```sh
npm ci
npm run check
npm test
npm run build
npm run test:native
```

`test:native` 默认只读读取 macOS 的 `/Applications/Obsidian.app/Contents/Resources/obsidian.asar`，提取待核验方法到进程内存，核对指纹后在隔离环境运行过滤器。它不启动真实 Sync 实例、不打开仓库或 Sync 数据库、不进行网络请求，也不把原生源码写入项目交付物。

自定义输入：

```sh
npm run test:native -- --asar /absolute/path/to/obsidian.asar
npm run test:native -- --app-js /absolute/path/to/app.js
```

使用 `--app-js` 时，应另外保存该输入的平台和版本来源；单个脚本文件不能独立证明来源平台。检查脚本仅识别已核验的构建布局，布局变化或指纹不匹配应停止，而不是猜测定位。

保留输出中的构建摘要、方法核对结果、离线断言结果和限制说明。计数只能从本次实际输出引用；不能把未运行的平台写成“同样通过”。

## 真实设备验证准备

优先使用专门的测试仓库和测试远端，放入无敏感内容的笔记及可丢弃测试插件。不要以生产仓库中“暂时没有看到变化”作为传输过滤成功的证据。

逐台记录：

- 设备名称及绑定的位置：电脑、手机或 iPad。
- 操作系统版本、Obsidian 当前应用/API 版本，以及实际配置目录。
- 官方 Sync 的相关原生开关，尤其已安装社区插件与已启用社区插件列表。
- 应用前的原生排除列表、规则修订号、插件诊断和待变更预览。
- 本机自动处理开关、已有 ID 基线、新安装来源记录路径及到达时间、自动处理状态与等待原因。
- 测试文件的具体内容、修改时间及校验摘要，操作顺序和 Sync 日志。

手机与 iPad 必须分别核验。各设备先检查兼容诊断，只有全部门禁通过后才可本机确认实验适配并继续测试；若失败，应向维护者提供版本与诊断，保持只读。新安装观察方法还有独立的版本/指纹检查，不能因为 Sync 写入检查通过就默认安装来源识别也已通过。不能通过删掉只读判断、伪造版本或替换指纹来绕过验证。通过门禁只说明具备运行实验的条件，不说明网络、持久化或该移动平台已经通过端到端验收。

在初始设置和切换测试规则前，通过原生 Sync 设置暂停同步，尽量减少并发。暂停不等于撤销已有传输；恢复时记录时间并检查日志。不得把配置过程描述成全设备同时生效。

## 待执行的端到端用例

以下是测试过程，不是当前版本已经完成的测试结果。移动端写入用例仅可在全部本机兼容门禁通过、用户明确开启实验适配后执行，且应先使用可丢弃测试仓库。

1. **基线传输。** 不排除测试插件时，在源设备修改测试插件目录中的程序文件和 `data.json`，确认另一设备实际收到；同时验证普通笔记。若基线本就不传输，后面的“未收到”不能作为排除生效的证据。
2. **排除下载。** 在接收设备绑定位置、预览并应用排除，确认原生列表出现精确目录。恢复 Sync 后，从另一设备制造带唯一标记的新版本，检查被排除设备的本地内容与日志；普通笔记和邻近插件目录应继续传输。
3. **排除上传。** 在被排除设备修改相同测试插件目录，确认另一设备未接收到，同时用普通笔记确认 Sync 正常工作。排除是双向的，不能只验证下载。
4. **启用列表独立。** 保持测试插件目录排除，单独验证 `community-plugins.json` 的行为，确认它由原生列表同步开关决定。不要把目录排除误解为启用状态保护。
5. **已有文件保留。** 应用排除后，本机未另行确认清理前，已有程序、设置和启用状态应保持不变，远端旧文件也不应被本插件主动删除。
6. **重启持久化。** 记录原生保存完成后的列表，完全退出 Obsidian，再打开；在插件未重新应用前检查原生排除列表与实际过滤行为。移动端需使用该平台的完全退出方式。记录结果，不能仅凭保存 Promise 推断通过。
7. **取消排除。** 先预览本插件拥有的目录，再明确恢复。检查原生 Sync 是否接收远端更新或删除，或上传本地修改。恢复资格可能触发此前积压的变更，这不是文件备份还原。
8. **用户排除保留。** 预先加入普通文件夹、上级目录和一个相同的插件目录。应用与恢复应保留这些用户项目；相似前缀的插件目录不能被误排除。
9. **自保护与自定义目录。** 验证无法排除 `device-plugin-sync`；在自定义配置目录的测试仓库验证精确路径，普通策略笔记仍可同步。
10. **版本与平台门禁。** 未知版本、指纹不匹配、Sync 未就绪以及未本机确认实验适配的移动端只能查看和预览，自动处理也不得写入原生排除列表。确认实验适配本身不得写入原生列表，也不能跳过任何门禁；升级或签名变化后应回到只读。验证这些情况下本插件未修改原生列表，并明确记录原生 Sync 没有被本插件暂停。
11. **未完成日志。** 在受控测试中模拟原生保存失败。当前列表等于操作前或操作后时，应要求明确核对并恢复对应所有权；两者都不相等时必须停止自动处理，保留当前列表供手工审查。
12. **移动端本机编辑。** 只同步规则文件和本管理插件，不预先下载清单中的测试插件。分别在手机/iPad 确认完整清单可见，仅本机列可编辑，全选/全不选正确；取消编辑和预览都不写规则或原生列表。最终确认后检查只有本机列变化、其他列和清单保留、本机排除项正确。未改选择时不增加修订号。让其他设备更新规则后再确认旧预览，检查会停止；单独测试规则保存后原生保存失败的提示与恢复。记录分布式同时离线编辑仍可能冲突，不能将本地冲突检查视为全局锁。
13. **清理确认和备份找回。** 在已暂停且无传输中的测试仓库应用不同步选择，确认只有已安装且被排除的插件进入清理列表；默认全不选，必须勾选插件并确认才可操作。清理整个插件目录后，核对隐藏备份包含程序和设置、启用清单字节不变、其他插件未变。分别验证取消、未暂停、仍在同步、版本/函数不匹配、文件变动、规则变动和中断时不继续移动。放回备份时禁止覆盖已有目录；保持原生排除，不自动启用。再恢复 Sync，双端核对远端插件文件未被清理。手机和 iPad 各自执行，不能用桌面结果代替。
14. **语言和易读性。** 切换中文/英文/跟随 Obsidian，核对新装默认跟随、旧记录升级保留中文，规则/设备名称/路径不变。检查主界面、预览、清理确认、备份找回、失败提示、恢复同步和故障处理的意思一致。本文案仅完成模拟用户审查，尚无真实用户可用性研究。
15. **停用与卸载。** 操作后确认已有原生排除项保留，不会因为插件停止运行而自动移除；停止新安装观察和自动处理，不能声称停用期间已可靠记录安装来源。

同一路径被外部移除后又重新加入，列表状态可能与原先完全相同。本插件无法识别这种来源变化，测试和文档应保留这一限制，不能声称所有权追踪覆盖了此情形。

## 0.3.0 新安装自动处理：待执行的真实设备用例

### 预期行为与记录位置

“自动设置新插件的同步范围”默认开启，仅影响本机。设备必须先绑定自己的名称、启用本插件，并允许官方 Sync 传输插件文件、插件设置、共享清单和安装记录。自动写入仍需 Sync 兼容检查通过；手机/iPad 仍需单独开启本机实验功能。

仅识别本插件运行期间从官方社区插件入口发起的**新安装**，不能仅因本地发现一个插件目录，就推断为本机安装。更新与清单中的已有 ID 不改变原有选择。

| 来源 | 所有 desktop 设备 | 来源 phone/tablet 设备 | 其他 phone/tablet 设备 |
| --- | --- | --- | --- |
| desktop | 允许 | 不适用 | 排除 |
| phone/tablet | 允许 | 允许 | 排除 |

安装来源写入普通同步笔记 `Device Plugin Sync/Installations/<installationId>/<pluginId>.md`。各端检查记录，将 `Policy.md` 中尚不存在的 ID 加入清单，已有 ID 不覆盖。来源目录分开可以减少不同安装写同一记录的冲突，但 `Policy.md` 仍是共享文件，不具备跨设备事务或锁。

在文件事件或定期检查时，只对本机新出现的 ID 应用同步默认值。首次升级、首次收到清单只建立当时已有 ID 的基线，不自动应用旧规则；已有 ID 的手动改动需要“查看并应用”。自动过程不得弹出清理窗口、移动文件、改写启用列表或自动启用插件。

### 场景与通过依据

以下每条均须记录时间、设备、API 版本、安装入口、来源记录、前后 `Policy.md`、本机自动状态、原生排除列表与 Sync 日志。手机和 iPad 应分别执行，不能互相替代。

1. **升级与首个清单基线。** 从 0.2.0 升级，以及新设备第一次收到已有清单时，准备几条尚未应用的旧选择。确认只保存已有 ID 基线，原生排除列表没有改动，没有清理提示。再手动应用旧选择，确认原有路径仍可管理。
2. **电脑官方新安装。** 保持本插件和自动处理开启、电脑已绑定，从官方社区插件入口安装一个可丢弃的新插件。确认在本机写入正确来源记录，清单只新增一个 ID、全部 desktop 允许且全部移动设备排除。接收端自动应用仅这个新 ID；修改过的旧 ID 不变。分别检验接收端的真实上传和下载限制。
3. **手机与 iPad 官方新安装。** 分别从手机、iPad 官方入口安装不同测试插件。确认来源移动设备和所有 desktop 允许，其他移动设备排除。核对来源设备标识而非只核对设备类型。电脑收到文件不代表插件已经启用；启用列表应未被本插件改写。
4. **更新、重装与已登记 ID。** 更新已登记插件；对已手动改变默认选择的插件进行允许的重装。确认不重新套用默认值、不复写旧选择、不把更新当成新安装。已有 ID 收到重复来源记录也应保持选择。
5. **只自动处理新 ID。** 同一次共享文件变化既包含一个新 ID，又包含旧 ID 的手动改动。新 ID 自动应用；旧 ID 对应的原生排除设置及管理记录应保持原样，直到用户主动“查看并应用”。自动处理状态不得声称整份清单均已应用。
6. **未识别来源与手动登记。** 分别测试 BRAT、手工复制、本插件未运行、自动开关关闭、尚无清单、尚未绑定的安装。不得仅按目录出现猜来源。完成设置并重新开启自动设置后，从“登记本机安装的插件”选择未登记插件，点击“确认这些插件是在本机安装的”；已登记 ID 不进入覆盖流程。验证刚从远端下载的插件不会自动被认成本机安装。
7. **开关与兼容限制。** 关闭本机开关、关闭手机实验功能、模拟未知版本、安装方法指纹变化、Sync 方法不匹配及 Sync 未就绪。核对没有绕过检查写入；应显示可理解的等待原因。修复原因并点击“检查新插件”后，确认只处理需要处理的新 ID。开关不应改变另一设备的本地设置。
8. **读写失败与重试。** 受控模拟来源记录、清单和本机记录读写失败，以及原生保存失败。确认未完成的新 ID 不被误记为已成功应用，等待原因保留，按现有故障处理流程检查后可以重试，不覆盖当前原生列表。失败后不得自动清理文件。
9. **到达顺序与首次下载。** 分别让插件文件、安装记录和 `Policy.md` 先后到达，记录自动处理发生的实际时间。确认最终选择与限制符合预期，但明确记录在限制生效前是否已有文件下载；不能用最终正确状态推断“从未下载”。邻近插件和普通笔记继续正常同步。
10. **并发与人工选择优先。** 用测试设备制造重复记录、同 ID 的不同来源记录、其他 ID 并行安装，以及手动编辑与自动合并交错。已登记 ID 的人工选择不得被自动默认值改写。记录实际冲突和恢复步骤；本地重读检查不能证明全局无覆盖，不能将来源记录分目录描述为跨设备锁。
11. **自动处理无清理、无自动启用。** 在接收端预先放入一个将被新规则排除的插件，核对文件与设置保留。确认无清理弹窗、无文件移动、启用列表字节不变。自动允许同步的插件是否启用仍由 Obsidian 及用户原有设置决定。
12. **重启与积压记录。** 自动应用后退出重开，核对原生限制和已处理 ID 状态；再接收积压的记录或重复事件，确认不重复覆盖手动选择。重新安装或清除本地数据后，检查基线与绑定状态，不能默认继承旧设备记录。

### 不能据此省略的边界

文件事件和定期检查均发生在信息到达之后，不是下载前的服务端拦截。即使最终排除列表正确，也无法保证首次插件文件没有先到达。自动流程不撤回进行中的传输，不删除已经下载的文件，也不会让另一设备上的插件自动启用。

测试必须分清“观察到安装”“来源记录已写入”“清单已合并”“本机限制已保存”“真实传输符合选择”五步。前三步成功不是后两步的证据。任何计数或通过结论只能来自真实执行记录；本节没有声明这些用例已经完成。

## 保存与故障恢复的证据解释

写入顺序是：本地记录预期变更 → 检查当前列表仍等于预览前状态 → 原生 `setIgnoreFolders()` → 同一调用栈发起原生 `saveData()` 并等待 → 重新检查列表 → 更新本地所有权及本机应用记录。

`setIgnoreFolders()` 自身返回 `void`，仅等待它不足以证明原生保存结束。这里等待的是原生保存操作；本插件不直接操作数据库，也不自动回滚可能已被其他操作修改的列表。只有真实重启复查可以补充重启持久化证据。

未完成日志的核对只用于恢复管理记录，不代替重新预览和应用规则。若当前列表既不等于操作前也不等于操作后，应手工核对；放弃管理记录会保留当前列表，不会自动恢复同步。

## 发布记录建议

每次发布附上简短记录：测试日期、提交/构建标识、桌面和移动端实际版本、命令与结果、真实设备用例结果、未执行项目。0.3.0 还应注明是否实际安装了新插件、安装来源观察是否运行，以及来源记录到真实排除生效的时间顺序。手机与 iPad 的结果分开写；没有共享回执时，不得根据电脑界面声称某台移动设备已经应用。

## 0.2.0 清理功能的额外检查

普通同步选择继续使用原来的 12 个方法指纹。可选清理另核对本地插件停止方法 `unloadPlugin` 和 Sync 主循环 `_sync`，并检查当前真实过滤器拒绝源路径及隐藏备份路径。只支持 `pause === true` 且 `syncing === false` 的状态；本插件不会自动暂停或恢复 Sync。

移动目录使用公开的 `DataAdapter.rename`，不永久删除、不调用原生卸载插件功能、不改写共享启用名单。停止运行中的插件依然依赖内部方法，不能因此宣称整个清理流程使用的都是公开 API。插件列表可能需要重启刷新；曾启用的插件在放回文件后重启可能再次加载。

备份清单先于文件移动写入；中断后可通过现存备份目录找回已移走的文件。清理无法保证不守规矩的第三方插件停止所有异步写入，也不证明真实跨设备删除传播已验收。必须通过本节对应的真实设备用例后补充证据。
